## Review findings for Claude

The [GitHub COMMENT review](https://github.com/lostfaithxenia/GLauncher/pull/5#pullrequestreview-5760448871) has inline comments anchored to the unchanged import. It is a Codex technical review using SYN's connected GitHub identity, not a fabricated independent-account approval.

### R1 — P1: cancelled launch waiting must not lose the session identity

Location: Sessions/SessionModels.cs, LaunchRequest / LaunchAsync, lines 87 and 104–110.

LaunchAsync creates/returns the session identity only through its eventual snapshot, while cancellation is documented to cancel waiting without killing an already-created process. If the wait is cancelled after a process exists, the caller can lose the identity needed to observe or terminate that launch. GameId alone cannot distinguish repeated or concurrent launches.

Requested: register before native side effects and make that registration recoverable using a caller-known SessionId/request identity or an immediate registration handle. Define pre-start cancellation, post-start cancellation and duplicate-request behavior. A cancelled wait must not create an unidentifiable or accidentally duplicated running session.

This is an API-contract gap identified by inspection, not a demonstrated native-process failure.

### R2 — P1: uncertain tracking needs non-destructive resolution and precise transitions

Location: Sessions/SessionModels.cs, UserDismissed and IGameSessionService, especially line 41.

TrackingUncertain is the right idea, but UserDismissed has no corresponding operation. Cancelling observation removes only the observer, and TerminateAsync cannot resolve a session whose termination capability is Unsupported. That leaves an uncertain session active indefinitely, potentially holding notification/inactivity policy in gameplay.

Requested: expose a stop-tracking/dismiss seam that does not kill processes. Distinguish dismissed tracking from positively observed game exit; the current Exited comment promises observation, which dismissal does not prove. Define how this affects GetActiveSessions / IsPossiblyAlive and UI labelling.

Also clarify that a root/bootstrap exit does not force uncertainty if a verified child is still running. Use TrackingUncertain for a lost/unverified continuation and retain Running while verified session processes are alive. An uncertainty reason/detail would help #2 explain a handoff or lost access.

### R3 — P2: keep ObserveAsync, specify the delivery contract

Location: Sessions/SessionModels.cs, line 120.

I would retain IAsyncEnumerable<SessionSnapshot>. It suits a Windows adapter fed by a background tracker and per-observer queues, without tying Core to a UI framework.

Requested documentation:
- An atomic current-state replay plus later snapshots, avoiding a GetSession → subscribe gap.
- Independent delivery to each observer.
- Ordering/coalescing and bounded slow-consumer behavior that cannot stall the tracker.
- Terminal replay/completion, unknown-session behavior and cancellation semantics.
- Snapshot collections are copies/immutable views, not live mutable tracker lists.

A shared consumable reader is not a broadcast contract. [Microsoft's channel documentation](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels) describes producer/consumer queues and backpressure; per-observer fan-out is the adapter design proposed here. This is not yet an implemented or tested watcher.

### R4 — P2: termination capability must distinguish ownership from completeness

Location: Sessions/SessionModels.cs, line 60 and termination result definitions.

Yes, I can implement the scoped TerminateAsync shape using an owned job or revalidated owned process handles. No arbitrary foreground-process kill is needed.

Clarify Supported versus Partial when every known process is owned but the game may have an unknown external continuation. Define unknown-survivor reporting and the resulting session state. An empty known survivor list must not prove that the whole game exited. Actual termination must revalidate session membership/process creation identity, with failures reported rather than broadened to unrelated processes.

The current enum shapes are usable; their guarantees need agreement before implementation.

### R5 — P2: preserve explicit termination under the launcher-exit policy

Location: ADR-001, line 81.

LeaveGameRunning is the appropriate default. Its enum value is also zero, but the runtime setting/orchestrator is not implemented here.

Remove or narrow the ADR's kill-on-job-close exception. Even when TerminateGame is selected for normal exit, game termination should go through explicit scoped TerminateAsync calls. Resource disposal or a crash must not silently become another termination operation.

[Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) that closing the last job handle with the kill-on-close flag terminates associated processes. Keep that flag off for the stated passive-disposal guarantee.
